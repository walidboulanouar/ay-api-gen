# Competitive Gap Analysis

> Researched 2026-07-25 via public web research (WebSearch/WebFetch, no signups, no authenticated access). 5 real, currently-shipping competitors, chosen to span the market: the direct "OpenAPI→MCP with a security angle" competitor our own PRODUCT.md already named (Speakeasy/Gram), the dominant open-source Python framework (FastMCP), the structurally-closest Node/TS CLI (openapi-mcp-generator), a no-code enterprise SaaS (DigitalAPI), and a platform-engineering-adjacent Python codegen tool (cnoe-io/openapi-mcp-codegen).
>
> Every claim below is sourced from a specific competitor's own docs, marketing pages, GitHub repo, or disclosed security advisory — not guessed. Where a subagent reported "not found" for a data point, that's carried through here rather than filled in.

## 1. What we're missing entirely

These are real capabilities that at least one shipping competitor has and we don't.

- **Alternative transports.** We only support stdio. `openapi-mcp-generator` ships stdio, SSE, StreamableHTTP, *and* a Cloudflare Worker deploy target. Gram is HTTP-hosted by construction. This is real, current-market table stakes for anyone who wants to run an MCP server as a reachable service rather than a subprocess Claude Code spawns. **→ Building tonight (see below).**
- **Hosted/managed serving.** Gram and DigitalAPI both offer "we host your MCP server" as the primary product. We're generate-and-self-host only. This is a real gap but requires standing up real hosting infrastructure (servers, DNS, TLS, uptime SLAs) — explicitly out of scope for a sandbox session with no live infra. **→ Documented in HUMAN-SETUP-NEEDED.md, not built.**
- **Interactive OAuth (PKCE + Dynamic Client Registration) for browser-based user login flows.** Speakeasy/Gram lead with OAuth 2.1 + PKCE + DCR for end-user-facing auth. We already automate the `client_credentials` grant (see `auth-codegen.js`'s OAuth2 token helper — this is more OAuth automation than `openapi-mcp-generator` or `cnoe-io` ship, both of which require fully manual token handling), but we don't do interactive authorization-code-with-browser-redirect flows. Building this needs a live OAuth provider to verify against end-to-end — can't be done or verified without live infra/secrets. **→ Documented, not built.**
- **Multi-tool workflow composition.** Gram lets you compose several atomic OpenAPI-derived tools into one higher-level "workflow" tool with business logic in between. We have `--slim` (prune to a token budget) and `--only`/`--exclude` (filter), which curate *which* tools ship, but nothing that composes *new* tools from existing ones. Genuine gap; real design work (a workflow DSL, execution semantics) that's bigger than a same-night add-on. **→ Documented, not built — candidate for a future dedicated session.**
- **LLM-assisted spec/description enhancement.** `cnoe-io/openapi-mcp-codegen` has an `--enhance-docstring-with-llm` flag that rewrites tool descriptions via an LLM for clarity. We deliberately do the opposite — cap and sanitize descriptions rather than expand them, because every character in a tool description is attacker-controllable prompt-injection surface (T-RUN-3). This is a **philosophical difference we're making explicit, not silently missing** — see Section 3.

## 2. What we have but they do better

- **Spec linting depth.** We ship `spec-linter.js` with 3 checks (T-API-1 unauth-mutating, T-API-2 sensitive-path-param, T-API-3 mass-assignment). DigitalAPI claims Spectral-based schema validation; Speakeasy's marketing claims "prompt injection and shadow MCP detection" at their gateway (mechanism undisclosed in their public docs — asserted, not demonstrated). Our own `THREAT-MODEL.md` (on the `security-threat-model` branch) defines T-API-4 (sensitive query param), T-API-5 (weak/no auth scheme declared globally), and T-API-6 (no rate limit) as follow-ups that were never built. **→ Extending T-API-4/T-API-5 tonight.**
- **Managed/enterprise governance UX.** Speakeasy/Gram and DigitalAPI both have real RBAC-to-the-tool-level, SSO, audit trails, and SIEM export at the *runtime gateway* layer. We have namespace collision protection and an audit trail is limited to whatever the operator's own MCP client logs. This is real, but it's fundamentally a hosted-service feature category — building a credible version requires a runtime service with persistent identity and session state, not a code-generation CLI. Out of scope for tonight; noted honestly rather than hand-waved.
- **Dependency ergonomics for consumers of the generated *CLI specifically.*** `openapi-mcp-generator`'s generated output includes a full TypeScript toolchain (tsc, eslint, prettier) and richer generated project scaffolding (HTML test clients for web transports). Our generated output is intentionally minimal (no build step, plain JS) — this cuts both ways (see Section 3) but means their generated projects have more batteries-included tooling if the target audience wants that.

## 3. What we already do better (evidence-backed, not just asserted)

This is the section worth being direct about, because two competitors handed us extremely concrete evidence.

- **We hardened preemptively; they patched after disclosure.** `FastMCP` shipped **CVE-2026-32871 / GHSA-vv7q-7jx5-f767** (High, CWE-918): unencoded path-parameter substitution let an attacker's `../` sequences escape the intended API prefix via `urllib.parse.urljoin()` — an **authenticated SSRF**, since the forged request still carried the configured auth headers. `openapi-mcp-generator` shipped **two** disclosed vulnerabilities in the same session's worth of work: issue #68, SSRF via uncontrolled external `$ref` resolution, and issue #67, **template-literal injection via unsanitized OpenAPI `description` fields that could expose `process.env` to MCP clients** — structurally the identical vulnerability class to our T-ING-1/T-GEN-1 fixes (S1/S2 of this project's own history), except we caught and fixed it before shipping, with regression tests, and they didn't. Worse for them: their SSRF fix (#68) **regressed within the same week** (#70), requiring an emergency point release — exactly the kind of "security theater retrofit" failure mode our `withFileLock`/`sanitizeApiName`/`assertHostAllowed`-style "verify the fix actually has teeth" testing discipline (revert-confirm-restore, documented throughout this project's `PROGRESS-LOG.md`) is designed to prevent. **This is our single strongest, most concrete claim: "not a security feature list — a track record of catching these classes of bug before they ship, with tests that prove it, while two direct competitors shipped them to production."**
- **Minimal, auditable dependency footprint.** We depend on exactly two packages, `@modelcontextprotocol/sdk` and `yaml`, both exact-pinned, `yaml` a zero-transitive-dependency leaf. `openapi-mcp-generator` pulls in `@apidevtools/swagger-parser`, `commander`, `openapi-types`, `json-schema-to-zod`, plus a full TypeScript build toolchain into every generated project. `cnoe-io`'s generator requires Python ≥3.13 plus `fastmcp`, `fastapi`, `httpx`, `pydantic`. Every extra dependency is extra supply-chain surface — this is not a marketing point, it's a directly measurable fact (`npm ls`) and matches our own threat model's R-02/R-05 concerns, already mitigated.
- **The only fully transparent, zero-signup, zero-cost security tool in the category.** `ay-api-gen audit --baseline` runs locally, requires no account, no API key, no network call beyond fetching the spec itself, and is source-available end to end. Speakeasy's pricing page is enterprise-contact-only. DigitalAPI's pricing is enterprise-contact-only. FastMCP Cloud's pricing page is behind an authenticated signup wall (couldn't even be read anonymously during this research). We're the only competitor in this set where a skeptical developer can `npm install` and read every line of what's checking their spec before trusting it with credentials.
- **Concurrency-safe writes.** File locking (`file-lock.js`, B-09) on `settings.json`/registry writes — not mentioned in any competitor's docs. Untested if any of them have it; safe to say it's not a claimed feature anywhere we looked.
- **Settings/config collision protection.** Namespaced `ay-api-gen:<name>` entries with refuse-or-`--force` semantics — `openapi-mcp-generator`'s research explicitly confirmed this is absent from that tool. A malicious or careless spec named e.g. `"github"` can't silently shadow another tool's credentialed MCP server entry in our output; nothing in the competitor research suggests any of the five tools we looked at do this.
- **Output-path and package.json injection protections** (T-GEN-2/T-GEN-4) — none of the five competitors' docs or source (as researched) mention path-traversal-via-`--output` protection or generated-package.json field-injection hardening at all.
- **Reverse generation (MCP tools → OpenAPI).** We ship this (`reverse.js`, since v0.1.0). FastMCP explicitly does **not** — it's an open, unresolved feature request (their issue #4107) with users pointed to a third-party tool (`mcpo`) instead. Neither `openapi-mcp-generator`, `cnoe-io`, nor DigitalAPI's public docs mention a reverse direction either.
- **Runtime response caching and rate limiting.** Opt-in, built into `runtime/mcp-server.js`. Not documented as a feature by any of the five competitors researched.
- **Full OpenAPI 3.1 handling with real regression coverage**, including the `nullable`-as-`type`-array migration, `components.pathItems` `$ref` resolution, and `webhooks` (parsed but correctly *not* turned into nonsensical outbound tools). FastMCP's own issue tracker shows a **user-reported breakage** on exactly the 3.0-vs-3.1 schema shape mismatch we specifically test for (their issue #1021). `openapi-mcp-generator` doesn't document 3.1 support explicitly at all, despite using a parser library that technically handles it.

## What we built tonight (buildable without live infra/secrets)

Picked for being real, evidence-backed gaps that don't require a live external service, a signup, a browser-redirect OAuth flow, or hosting infrastructure to build or verify — same production bar as the rest of this project: real code, real tests, no stubs.

1. **DONE — StreamableHTTP transport for `ay-api-gen serve`** (closed the "single transport" gap — `openapi-mcp-generator` and Gram both support HTTP-reachable MCP servers; we only supported stdio). `--transport http [--port 3000] [--host 127.0.0.1]`. Defaults to `127.0.0.1`-only binding with a loud warning required to bind more broadly, resolving the exact "needs a security-relevant decision" concern that deferred this back at backlog item 20 — now with competitor evidence that localhost-default is a reasonable, expected posture. Verified with a real `StreamableHTTPClientTransport` protocol roundtrip against an ephemeral fixture, not just a syntax check — and that verification caught a real bug: the SDK's stateless mode (`sessionIdGenerator: undefined`), which looked like the simpler/correct choice from the docs, actually 500s on the `notifications/initialized` message every real MCP session sends right after `initialize`. Switched to stateful mode (session ID per connection), confirmed working end-to-end.
2. **DONE — T-API-4 (sensitive data in query params) and T-API-5 (weak/no globally-declared auth scheme)** added to `spec-linter.js` — directly deepens the one area competitors (DigitalAPI, Speakeasy) claim to beat us on, using checks already scoped in our own threat model but never implemented.

See `PROGRESS-LOG.md` for what shipped, with test results.
